# Agent contracts

## Triage and discovery

Normalize the meeting, classify facts/assumptions/pending inputs, assign requirement IDs, and identify whether the process is formal, demonstrative, or incomplete. Do not select products.

## Solution architect

Evaluate the complete approved catalog against requirement IDs and shared gating rules. Produce explicit decisions for every product. Check coverage for DNS continuity, HTTP origin routing, web performance, L7 application protection, L3/L4 infrastructure DDoS, bot automation, and account abuse. Distinguish GTM from Application Load Balancer and App & API Protector from Prolexic. A recommended product may have a pending implementation modality; record those as separate fields. For every seasonal critical-event pain, create an event-readiness plan. Do not write commercial terms.

## Technical writer

Write client-specific content into the canonical template sections. Each front must connect business pain, technical mechanism, configuration scope, evidence, and expected outcome. Do not add products or resolve open facts by inference. Run the client-facing forbidden-language check before handoff.

## Technical QA

Verify architecture, product gating, traceability, feasibility, and measurable acceptance. Cross-check every material claim through `promise → component → implementation scope → acceptance evidence`; a broken chain is a blocking issue. Reject acceptance criteria whose outcome is materially controlled by the application, origin, network, browser, or an uncontracted third party. A post-baseline performance target must be approved by the Assessment exit gate; if it is not approved, the pre-agreed fallback is delivery of the decomposed baseline report, unless a commercial target was already promised. Architecture issues return to the architect.

## Commercial QA

Verify warranty, SLA, licensing, commitments, confidentiality, and unsupported claims against the source hierarchy. Classify each term as commitment, assumption, client pending, or internal POPULOS decision. Internal decisions block emission and never reach the client. Do not treat a template placeholder as a POPULOS standard. Preserve the fixed institutional SLA table without a second hedge. Prohibit double hedging: a statement cannot be both a commitment and an estimate or pending item. Text issues return to the writer.

## Repair

Perform deterministic mechanical fixes only: insert missing authorized structure, normalize status, repair numbering, and reject unresolved placeholders or forbidden client-facing language. Insertion is the default operation. Removal or replacement of scope, deliverables, requirements, acceptance criteria, responsibilities, or commitments requires an explicit issue authorizing that exact change. Repair never invents an estimate and never changes architecture.

## Compositor

Use code to map the approved proposal state into the source DOCX. It does not author content and cannot infer missing fields. Fixed-capacity mappings must assert before writing; silent truncation is forbidden. When authorized content exceeds the template slots, insert new structure or block emission. After composition, compare the normalized client-visible state with the DOCX and block any unexplained omission. Block before rendering when any internal POPULOS decision is unresolved. Delivery gates: no unresolved guillemets or double brackets; no semantic placeholders such as `item requisito`, `requisito correspondente`, `TBD`, or drafting labels; no empty trailing columns; no colored schedule cells without legible text; no orphan heading; no split callout title/body styling; and no pipeline vocabulary.

Institutional exceptions are versioned by template ID, template version, full-file SHA-256, and individual block hashes. A mismatch invalidates the exception and blocks emission until the whitelist is reviewed and versioned again. Lists must use native DOCX numbering copied from the approved template; typed bullet characters are forbidden.
